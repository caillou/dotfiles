# Bootstrap and verify the new Mac

## PRD

[2026-09-10-chezmoi-mac-bootstrap](../prd.md)

Captured values, commands and sources are in [research-notes.md](../research-notes.md).

## What to build

Run the one-line bootstrap on the managed Mac and verify the result against the PRD.

- Preconditions: `sudo -v` works for the local account; Command Line Tools already installed there (they are).
- Run the bootstrap and every later `chezmoi apply` from Terminal.app with iTerm2 closed. Script 63 leaves the iTerm2 keys alone while iTerm2 runs, because a running iTerm2 saves its stock preferences over the repo plist on quit. Seen on 2026-09-14: the plist came back as repo drift with a fresh Default profile; the fix was `git checkout .iterm2`, `chezmoi apply`, then opening iTerm2.
- Run the one-liner with built-in git, `--purge-binary` and the source flag (`--promptDefaults` not used; answer the prompts); answer the group prompts (personal no, embedded no); watch for the Homebrew sudo prompt, the gh browser login, and two Automation consent prompts, one for System Events (the wallpaper) and one for System Settings, which the defaults script quits by Apple Event.
- Walk the printed manual checklist: privacy approvals, Azure DevOps key paste, Karabiner first launch, dictation consent.
- Verify: fish prompt and abbreviations; Downloads view; Cmd+N; screenshots; trackpad settings incl. tap to click; Fn keys; natural scroll off; Dock app list and appearance; black wallpaper; click on wallpaper does nothing; widgets hidden; desktop icons hidden; dictation double-Control; power settings; auto-brightness off; iTerm2 profile; git identity in an ICFM clone; asdf versions; Karabiner rules and the Hammerspoon Ctrl+S layout if the apps were provided; `git push` from the dotfiles checkout works.
- Run the apply a second time and watch the display script: it must say auto-brightness is already off, import nothing and restart no daemon, at most one password prompt. If it imports and restarts again, `corebrightnessd` is dropping the flag from entries it does not manage; record that, and the read-back or the write then has to tolerate keyless entries.
- Reboot once and check whether the pointer speed persisted and whether System Settings shows it; record the outcome in the research notes and, if it didn't persist, move pointer speed to the manual checklist.
- Record any Intune-blocked step in the research notes.
